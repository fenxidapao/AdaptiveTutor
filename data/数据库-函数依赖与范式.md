# 数据库 · 函数依赖与范式

关系模式设计的目标是减少冗余、避免插入/删除/更新异常。规范化的理论工具是**函数依赖**，逐级标准是**范式（NF）**。

## 函数依赖（Functional Dependency）

设 R 的属性集，X、Y 为子集。若 R 的任意两个元组在 X 上取值相同，则在 Y 上取值也必相同，则称 **X 函数决定 Y**，记作 X → Y（Y 函数依赖于 X）。

- **完全函数依赖**：Y 依赖于 X 的整体，去掉 X 任一属性则依赖不成立。
- **部分函数依赖**：Y 依赖于 X 的某个真子集。
- **传递函数依赖**：X→Y、Y→Z 且 Y 不→X、Z 不含于 Y，则 X 传递决定 Z。

**候选键**：能函数决定全体属性的最小属性集；候选键之一定为主键。包含在任一候选键中的属性为主属性，否则为非主属性。

## 第一范式（1NF）

属性不可再分（原子性），即表中每个单元格是单一值，不允许重复组或多值属性。是关系模型的基本要求。

## 第二范式（2NF）

满足 1NF，且**非主属性对候选键完全函数依赖**（消除非主属性对键的**部分依赖**）。仅当候选键为组合键且存在非主属性只依赖其中部分属性时才可能违反 2NF。分解方法：将部分依赖的属性与其决定因素单独成表。

## 第三范式（3NF）

满足 2NF，且**非主属性不传递依赖于候选键**（消除传递依赖）。即不存在 X→Y、Y→Z 使非主属性 Z 经 Y 传递依赖于键。分解方法：将传递链 Y→Z 单独成表。

## BC 范式（BCNF / Boyce-Codd）

比 3NF 更严：任一非平凡函数依赖 X→Y，X 都必须包含候选键（即决定因素必为超键）。3NF 允许主属性对键的传递/部分依赖，BCNF 不允许。一个满足 3NF 但不满足 BCNF 的典型例子：关系（学生, 课程, 教师），若一门课只由一位教师教（课程→教师），则课程→教师而课程不是超键，违反 BCNF，需分解为（课程,教师）与（学生,课程）。

## 范式对比小结

| 范式 | 消除的问题 | 要求 |
|---|---|---|
| 1NF | 属性可再分 | 原子值 |
| 2NF | 非主属性对键的部分依赖 | 完全函数依赖 |
| 3NF | 非主属性对键的传递依赖 | 非主属性不传递依赖键 |
| BCNF | 主属性对键的部分/传递依赖 | 决定因素均为超键 |

## 模式分解

将低范式关系分解为若干高范式关系，需保证**无损连接**（分解后自然连接能恢复原关系）和尽量**保持函数依赖**。通常借助属性闭包、候选键求解与依赖投影完成。过度规范化会增加连接开销，实际设计常在 3NF/BCNF 与查询性能间权衡。
